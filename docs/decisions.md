# Принятые решения

## React + Vite вместо Next.js (pr-001)

Приложение — личный кабинет за авторизацией: его страницы не нужно индексировать поисковикам, поэтому серверный рендеринг Next.js ничего не даёт. Клиентское приложение на Vite проще превратить в PWA с офлайн-режимом, в нём удобнее запускать ONNX-модель в Web Worker и открывать его как Telegram WebApp. Собранная статика раздаётся любым веб-сервером.

## Vitest вместо Jest (pr-001)

Vitest использует конфигурацию Vite (плагины, TypeScript без отдельного транспайлера), а его API совместим с Jest — тесты с Testing Library пишутся так же. Юнит-тесты UI-кита в pr-018 тоже будут на Vitest.

## Tailwind CSS 4 (pr-001)

Подключён через плагин `@tailwindcss/vite`, отдельные конфиги PostCSS и Tailwind не нужны.

## CI с первого PR (pr-001)

В плане фронтенда нет отдельной задачи на CI, поэтому GitHub Actions добавлен сразу: на каждый PR и push в `main` выполняются проверка типов, тесты и сборка.

## ESLint, Prettier и Stylelint (pr-002)

- ESLint 9 с плоским конфигом: базовые правила, typescript-eslint с проверками на основе типов, правила хуков React, react-refresh для Vite и jsx-a11y для доступности. Версия 9, а не 10: `eslint-plugin-jsx-a11y` пока поддерживает только ESLint до 9-й версии, а проверять доступность нужно с самого начала (в плане есть pr-094).
- Prettier отвечает за форматирование: без точек с запятой, одинарные кавычки. Плагин `prettier-plugin-tailwindcss` сортирует классы Tailwind в рекомендованном порядке. Правила ESLint, которые конфликтуют с Prettier, отключены через `eslint-config-prettier`.
- Stylelint со стандартным набором правил. Директивы Tailwind 4 (`@theme`, `@utility`, `@apply` и т. д.) разрешены, импорт — строкой, как в документации Tailwind.
- Все проверки выполняются в CI.

## Atomic Design и алиас `@/` (pr-003)

- Компоненты разложены по уровням `atoms` → `molecules` → `organisms` → `templates`; страницы лежат в `src/pages`, корень приложения — в `src/app`. Правило зависимостей: компонент использует только компоненты своего или более низкого уровня. Описание уровней — в `src/components/README.md`.
- Один компонент — один файл, тест лежит рядом (`Logo.tsx` и `Logo.test.tsx`). Без barrel-файлов `index.ts`: они мешают горячей перезагрузке и разбиению бандла.
- Алиас `@/` указывает на `src/` и настроен в `tsconfig.app.json` и `vite.config.ts`, поэтому импорты не зависят от глубины вложенности: `@/components/atoms/Logo`.
- Именованные экспорты вместо экспортов по умолчанию: имя компонента одинаковое во всех файлах, и его проще найти поиском.

## Zustand вместо Redux Toolkit (pr-004)

Данные с сервера (участки, диагнозы, прогнозы) будет хранить и кэшировать TanStack Query (pr-005). Глобального клиентского состояния остаётся немного: интерфейс, сессия пользователя, выбранные слои карты. Для этого достаточно Zustand: хранилище — это один хук без провайдеров, экшенов и редьюсеров, а компонент перерисовывается только при изменении выбранной части состояния. Хранилища лежат в `src/store`, по одному файлу на область.

## Axios + TanStack Query (pr-005)

- Axios — HTTP-клиент с общими настройками (`src/api/client.ts`): базовый адрес из `VITE_API_URL`, таймаут 15 с.
- Interceptor запроса добавляет заголовок `Authorization: Bearer …`, если есть токен. Откуда брать токен, решает модуль авторизации (pr-014): он передаст функцию в `setTokenProvider`, и клиент не будет зависеть от способа хранения токена.
- Interceptor ответа превращает любые сбои в `ApiError` со статусом и понятным текстом: из поля `detail` ответа FastAPI или «Сервер недоступен», если ответа нет. Интерфейсу не нужно разбирать ошибки Axios.
- TanStack Query хранит и кэширует данные с сервера: данные считаются свежими 30 с. При ошибках 4xx запрос не повторяется — ответ не изменится, — при сбоях сети и 5xx делаются ещё две попытки.
- В режиме разработки Vite проксирует `/api` на `http://127.0.0.1:8000`, поэтому фронтенд и бэкенд работают вместе без настройки CORS.
- В тестах запросы перехватывает MSW на уровне сети. Код приложения не знает о моках, а неожиданный запрос роняет тест (`onUnhandledRequest: 'error'`).

## Базовый UI-кит (pr-006)

- Компоненты написаны на Tailwind без сторонней библиотеки компонентов: внешний вид полностью свой, а в бандл не попадает лишний код. Варианты (`primary`, `secondary`, `ghost`, `danger`) и размеры кнопки описаны обычными объектами классов, без class-variance-authority: вариантов мало.
- Классы склеивает `cn` (`clsx` + `tailwind-merge`). `tailwind-merge` убирает конфликтующие классы, поэтому `className`, переданный снаружи, перекрывает стиль по умолчанию, а не зависит от порядка классов в CSS.
- Атомы принимают все атрибуты своего HTML-элемента и `ref` (в React 19 это обычный проп, `forwardRef` не нужен), поэтому подключаются к React Hook Form (pr-011) без обёрток.
- Кнопка по умолчанию `type="button"`: случайная кнопка внутри формы не отправит её. Во время загрузки кнопка заблокирована, показывает индикатор и помечена `aria-busy`.
- `Field` — подпись, подсказка и ошибка вокруг любого поля. Он сам создаёт `id` через `useId` и передаёт полю `aria-describedby` и `aria-invalid`, так что экранные дикторы читают подсказку и ошибку, а стиль ошибки поле берёт из `aria-invalid`. Само поле передаётся функцией: одна обёртка подходит для `Input`, `Textarea` и будущих выпадающих списков (pr-008).
- Включён `strict` в `tsconfig`: строгая типизация обязательна по правилам проекта, а в pr-001 её не включили. Код уже ей соответствовал, ошибок не появилось.

## Карточки, модальные окна, скелетоны (pr-007)

- Модальное окно построено на нативном `<dialog>` с `showModal()`. Браузер сам удерживает фокус внутри окна, делает остальную страницу недоступной (`inert`), закрывает окно по Esc и возвращает фокус на кнопку, которая его открыла. Библиотека для фокус-ловушки не нужна. Окно управляется пропом `open`; закрытие по Esc, кнопкой «Закрыть» или кликом по фону вызывает `onClose`. Прокрутка страницы под открытым окном отключена в CSS (`html:has(dialog[open])`).
- В jsdom у `<dialog>` нет `showModal()` и `close()`, поэтому тесты подставляют минимальную замену в `src/test/setup.ts`.
- `Card` — секция с необязательными заголовком, описанием и действиями. Если заголовок задан, секция подписана им (`aria-labelledby`) и видна дикторам как отдельная область.
- Скелетоны скрыты от экранных дикторов (`aria-hidden`), а о загрузке сообщает контейнер с `role="status"` и скрытым текстом «Загрузка…»: иначе диктор прочитал бы набор пустых блоков.

## Таблицы, пагинация, выпадающие списки (pr-008)

- Выпадающий список — нативный `<select>` со своей стрелкой. На телефонах он открывается системным выбором, а клавиатура и экранные дикторы работают без доработок; кастомный список пришлось бы делать с ролями `combobox` / `listbox` и ручным управлением фокусом. Если понадобится поиск по списку (например, по сортам винограда), для него будет отдельный компонент.
- `DataTable` описывается столбцами: заголовок, функция ячейки и выравнивание. Строки приходят готовыми, поэтому таблица одинаково работает с данными из TanStack Query и из тестов. Подпись (`caption`) скрыта визуально, но обязательна: диктор называет таблицу. Состояния загрузки (скелетоны) и пустого списка встроены. На узком экране таблица прокручивается по горизонтали внутри своей рамки.
- Сортировки в таблице нет: порядок строк будет задавать сервер вместе с постраничной выборкой (pr-014), а сортировка только по загруженной странице вводила бы в заблуждение.
- Пагинация показывает первую и последнюю страницы и окно вокруг текущей; пропуск в одну страницу показывается самой страницей, а не многоточием. Логика расчёта номеров вынесена в `getPageItems` и тестируется отдельно. Текущая страница помечена `aria-current="page"`, на единственной странице панель не рисуется.

## Layout: Header, Sidebar, Footer (pr-009)

- `DashboardTemplate` собирает каркас кабинета: шапка, боковая панель, содержимое, подвал. Страница передаёт только пункты меню и содержимое. Первой в порядке табуляции идёт ссылка «Перейти к содержимому»: клавиатурному пользователю не нужно проходить всё меню на каждой странице.
- Боковая панель на телефоне — выдвижное меню поверх страницы с затемнением, на широком экране (`lg`) — постоянная колонка. Закрытая панель на телефоне скрыта целиком (`hidden`), а не уведена за край экрана, поэтому её ссылки не попадают в порядок табуляции. Закрывается кликом по затемнению, Esc и переходом по ссылке. Кнопка меню в шапке сообщает состояние через `aria-expanded` и связана с панелью через `aria-controls`.
- Состояние панели хранит `useUiStore` из pr-004: шапка и панель — разные компоненты и не должны зависеть друг от друга.
- Пункты меню — обычные ссылки `<a href>`. Маршрутизатор подключится вместе со страницей 404 (pr-010), тогда ссылки заменятся на ссылки маршрутизатора; текущий пункт задаётся полем `current`, а его вычисление по адресу появится вместе с маршрутами.

## Маршрутизация, страница 404 и Error Boundary (pr-010)

- Маршрутизатор — `react-router` (режим data router: `createBrowserRouter` + `RouterProvider`). Маршруты описаны данными в `src/app/routes.tsx`, а не вложенными элементами: так их можно проверять тестами через `createMemoryRouter`, не открывая браузер. Роутер создаётся внутри `App` (`useState`), а не при загрузке модуля, поэтому тесты не зависят от адреса окна.
- Два уровня защиты от ошибок. Корневой маршрут имеет `errorElement`: ошибка отрисовки любой страницы показывает экран «Что-то пошло не так» вместо пустого окна, а шапка и провайдеры остаются работать. Выше стоит `ErrorBoundary` в `AppProviders` — последний рубеж для ошибок вне маршрутов, например в самих провайдерах. Перехватывать ошибки отрисовки умеют только классовые компоненты, поэтому `ErrorBoundary` — единственный класс в проекте.
- `ErrorPage` предлагает «Обновить страницу» (перезагрузка окна): после сбоя состояние компонента неизвестно, а перезагрузка гарантированно его очищает. `ErrorBoundary` принимает функцию запасного экрана с `reset` и необязательный `onError`: туда позже подключится отправка ошибок на сервер (pr-092).
- Страница 404 — маршрут `*`, поэтому любой неизвестный адрес получает одну страницу с понятным текстом и ссылкой на главную.
- Ссылки в шапке и боковом меню заменены на `Link` из `react-router`: переход происходит без перезагрузки страницы. Вычисление текущего пункта меню по адресу появится вместе с первыми страницами кабинета.
- Для production-сборки веб-сервер должен отдавать `index.html` на любой адрес (SPA fallback); в режиме разработки Vite делает это сам.

## Форма входа: React Hook Form + Zod (pr-011)

- Форма — React Hook Form: поля неуправляемые (значения читаются при отправке), поэтому ввод не перерисовывает форму на каждую букву. Правила проверки — схема Zod в `src/schemas/auth.ts`, подключённая через `zodResolver`; та же схема даёт тип значений формы (`z.infer`), так что правила и тип не расходятся. Сообщения об ошибках — по-русски, в схеме.
- У формы `noValidate`: ошибки показывает Zod, а не встроенная проверка браузера на языке системы. Каждая ошибка связана с полем (`aria-invalid`, `aria-describedby` — через `Field` из pr-006), общая ошибка выводится в блоке `role="alert"`.
- При входе пароль только обязателен, его длину и состав не проверяем: правила пароля действуют при регистрации (pr-012), а старый пароль мог быть создан по прежним правилам. Email обрезается по краям.
- Форма не знает про сеть: она принимает функцию `onSubmit` и показывает ошибку, которую та бросила. Текст `ApiError` (поле `detail` ответа сервера, например «Неверный email или пароль») выводится как есть, любая другая ошибка даёт «Не удалось войти». Пока идёт отправка, кнопка заблокирована: двойной клик не отправит запрос дважды.
- Контракт входа, на который рассчитан клиент: `POST /auth/login` с JSON `{ email, password }` возвращает `{ access_token, refresh_token, token_type: "bearer" }`. Это нужно сверить с бэкендом при реализации `/auth/login` (backend/pr-019); если он станет принимать форму `application/x-www-form-urlencoded`, изменится только `src/api/auth.ts`.
- После успешного входа выполняется переход на главную. Сохранение токенов и подстановку их в запросы добавит pr-014, защиту маршрутов — pr-015.
- Для тестов форм добавлен `@testing-library/user-event`: он печатает по символам и нажимает кнопки так же, как пользователь, и ловит ошибки, которых не видно при `fireEvent`.
- `AuthTemplate` — общий каркас страниц входа, регистрации и восстановления пароля (pr-012, pr-013). Ссылки на них из формы входа появятся вместе с этими страницами.

## Форма регистрации с выбором роли (pr-012)

- Выбрать при регистрации можно «Виноградарь» (`user`) и «Агроном» (`agronomist`); роли администратора в списке нет, а схема Zod её отклоняет. Администратора назначает только администратор: иначе любой мог бы выдать себе все права. Роль агронома даёт право подтверждать диагнозы (pr-052), поэтому сервер не должен слепо доверять самостоятельному выбору — подтверждение агронома администратором решается в ролевой модели (backend/pr-022). Форма отправляет выбранную роль как заявленную.
- Правила пароля: от 8 до 128 символов, хотя бы одна буква (любого алфавита, `\p{L}`) и одна цифра. Минимум 8 символов и отсутствие «только цифры» отсекают самые слабые пароли без требований вроде спецсимволов, которые лишь подталкивают к предсказуемым заменам. Верхняя граница нужна, потому что хэширование Argon2 (pr-016) на очень длинной строке — лёгкая нагрузка на сервер. Те же правила должен проверять бэкенд (pr-018): проверка в форме — удобство для пользователя, а не защита.
- Подтверждение пароля проверяется схемой (`refine` с ошибкой у поля подтверждения) и серверу не отправляется: `register()` отправляет только email, пароль, имя и роль. Поля пароля помечены `autocomplete="new-password"`, поэтому менеджер паролей предлагает сгенерировать и сохранить новый, а не подставляет старый.
- Занятый email (ответ 409) показывается у поля email собственным текстом, а не общей ошибкой формы: пользователь сразу видит, что менять. Любая другая ошибка сервера выводится блоком над кнопкой.
- После регистрации выполняется переход на страницу входа с сообщением «Аккаунт создан»: сообщение передаётся в состоянии маршрута и пропадает при обновлении страницы. Автоматический вход после регистрации не делается: токены сохраняет отдельный модуль (pr-014), а вход всё равно подтверждает, что пользователь знает пароль.
- Контракт, на который рассчитан клиент: `POST /auth/register` с JSON `{ email, password, full_name, role }` возвращает созданного пользователя `{ id, email, full_name, role }` с кодом 201, а занятый email — код 409. Сверить с бэкендом при реализации `/auth/register` (backend/pr-018).
- Страницы входа и регистрации ссылаются друг на друга; общий каркас — `AuthTemplate`, у него появилось место для нижней ссылки.

## Восстановление пароля (pr-013)

- Восстановление — два шага на двух страницах. `/forgot-password`: пользователь вводит email и получает письмо со ссылкой. `/reset-password?token=…`: по ссылке из письма задаётся новый пароль. Ключ берётся из адреса страницы; без него страница объясняет, что ссылка неполная, и предлагает запросить новую. Ключ не показывается на экране и не сохраняется.
- После запроса страница пишет «Если аккаунт с адресом … существует, мы отправили письмо» и не подтверждает, что аккаунт есть. Сервер отвечает одинаково для любого адреса: иначе форма позволяла бы перебором узнавать, какие email зарегистрированы. Тот же приём должен соблюдать бэкенд (backend/pr-024).
- Правила нового пароля вынесены в одну схему и общие для регистрации и сброса: пароль, допустимый при регистрации, нельзя нарушить при смене. Поля помечены `autocomplete="new-password"`.
- Ошибка сервера при установке пароля (например, «Ссылка устарела») показывается как есть, рядом остаётся ссылка «Запросить новую ссылку»: пользователь не оказывается в тупике. После успешной смены переход на вход с сообщением «Пароль изменён»; автоматический вход не делается, пока токены не сохраняются модулем из pr-014.
- Страница входа получила ссылку «Забыли пароль?»; сообщения «Аккаунт создан» и «Пароль изменён» передаются состоянием маршрута, поэтому исчезают при обновлении страницы.
- Контракт, на который рассчитан клиент (сверить с бэкендом в backend/pr-024): `POST /auth/password-reset` с `{ email }` отвечает 202 всегда; `POST /auth/password-reset/confirm` с `{ token, new_password }` отвечает 204, а при неверном или устаревшем ключе — 400 с текстом в `detail`.
