# Принятые решения

## React + Vite вместо Next.js (pr-001)

Приложение — личный кабинет за авторизацией: его страницы не нужно индексировать поисковикам, поэтому серверный рендеринг Next.js ничего не даёт. Клиентское приложение на Vite проще превратить в PWA с офлайн-режимом, в нём удобнее запускать ONNX-модель в Web Worker и открывать его как Telegram WebApp. Собранная статика раздаётся любым веб-сервером.

## Vitest вместо Jest (pr-001)

Vitest использует конфигурацию Vite (плагины, TypeScript без отдельного транспайлера), а его API совместим с Jest — тесты с Testing Library пишутся так же. Юнит-тесты UI-кита в pr-018 тоже будут на Vitest.

## Tailwind CSS 4 (pr-001)

Подключён через плагин `@tailwindcss/vite`, отдельные конфиги PostCSS и Tailwind не нужны.

## CI с первого PR (pr-001)

В плане фронтенда нет отдельной задачи на CI, поэтому GitHub Actions добавлен сразу: на каждый PR и push в `main` выполняются проверка типов, тесты и сборка.

## ESLint, Prettier и Stylelint (pr-002)

- ESLint 9 с плоским конфигом: базовые правила, typescript-eslint с проверками на основе типов, правила хуков React, react-refresh для Vite и jsx-a11y для доступности. Версия 9, а не 10: `eslint-plugin-jsx-a11y` пока поддерживает только ESLint до 9-й версии, а проверять доступность нужно с самого начала (в плане есть pr-094).
- Prettier отвечает за форматирование: без точек с запятой, одинарные кавычки. Плагин `prettier-plugin-tailwindcss` сортирует классы Tailwind в рекомендованном порядке. Правила ESLint, которые конфликтуют с Prettier, отключены через `eslint-config-prettier`.
- Stylelint со стандартным набором правил. Директивы Tailwind 4 (`@theme`, `@utility`, `@apply` и т. д.) разрешены, импорт — строкой, как в документации Tailwind.
- Все проверки выполняются в CI.

## Atomic Design и алиас `@/` (pr-003)

- Компоненты разложены по уровням `atoms` → `molecules` → `organisms` → `templates`; страницы лежат в `src/pages`, корень приложения — в `src/app`. Правило зависимостей: компонент использует только компоненты своего или более низкого уровня. Описание уровней — в `src/components/README.md`.
- Один компонент — один файл, тест лежит рядом (`Logo.tsx` и `Logo.test.tsx`). Без barrel-файлов `index.ts`: они мешают горячей перезагрузке и разбиению бандла.
- Алиас `@/` указывает на `src/` и настроен в `tsconfig.app.json` и `vite.config.ts`, поэтому импорты не зависят от глубины вложенности: `@/components/atoms/Logo`.
- Именованные экспорты вместо экспортов по умолчанию: имя компонента одинаковое во всех файлах, и его проще найти поиском.

## Zustand вместо Redux Toolkit (pr-004)

Данные с сервера (участки, диагнозы, прогнозы) будет хранить и кэшировать TanStack Query (pr-005). Глобального клиентского состояния остаётся немного: интерфейс, сессия пользователя, выбранные слои карты. Для этого достаточно Zustand: хранилище — это один хук без провайдеров, экшенов и редьюсеров, а компонент перерисовывается только при изменении выбранной части состояния. Хранилища лежат в `src/store`, по одному файлу на область.

## Axios + TanStack Query (pr-005)

- Axios — HTTP-клиент с общими настройками (`src/api/client.ts`): базовый адрес из `VITE_API_URL`, таймаут 15 с.
- Interceptor запроса добавляет заголовок `Authorization: Bearer …`, если есть токен. Откуда брать токен, решает модуль авторизации (pr-014): он передаст функцию в `setTokenProvider`, и клиент не будет зависеть от способа хранения токена.
- Interceptor ответа превращает любые сбои в `ApiError` со статусом и понятным текстом: из поля `detail` ответа FastAPI или «Сервер недоступен», если ответа нет. Интерфейсу не нужно разбирать ошибки Axios.
- TanStack Query хранит и кэширует данные с сервера: данные считаются свежими 30 с. При ошибках 4xx запрос не повторяется — ответ не изменится, — при сбоях сети и 5xx делаются ещё две попытки.
- В режиме разработки Vite проксирует `/api` на `http://127.0.0.1:8000`, поэтому фронтенд и бэкенд работают вместе без настройки CORS.
- В тестах запросы перехватывает MSW на уровне сети. Код приложения не знает о моках, а неожиданный запрос роняет тест (`onUnhandledRequest: 'error'`).

## Базовый UI-кит (pr-006)

- Компоненты написаны на Tailwind без сторонней библиотеки компонентов: внешний вид полностью свой, а в бандл не попадает лишний код. Варианты (`primary`, `secondary`, `ghost`, `danger`) и размеры кнопки описаны обычными объектами классов, без class-variance-authority: вариантов мало.
- Классы склеивает `cn` (`clsx` + `tailwind-merge`). `tailwind-merge` убирает конфликтующие классы, поэтому `className`, переданный снаружи, перекрывает стиль по умолчанию, а не зависит от порядка классов в CSS.
- Атомы принимают все атрибуты своего HTML-элемента и `ref` (в React 19 это обычный проп, `forwardRef` не нужен), поэтому подключаются к React Hook Form (pr-011) без обёрток.
- Кнопка по умолчанию `type="button"`: случайная кнопка внутри формы не отправит её. Во время загрузки кнопка заблокирована, показывает индикатор и помечена `aria-busy`.
- `Field` — подпись, подсказка и ошибка вокруг любого поля. Он сам создаёт `id` через `useId` и передаёт полю `aria-describedby` и `aria-invalid`, так что экранные дикторы читают подсказку и ошибку, а стиль ошибки поле берёт из `aria-invalid`. Само поле передаётся функцией: одна обёртка подходит для `Input`, `Textarea` и будущих выпадающих списков (pr-008).
- Включён `strict` в `tsconfig`: строгая типизация обязательна по правилам проекта, а в pr-001 её не включили. Код уже ей соответствовал, ошибок не появилось.

## Карточки, модальные окна, скелетоны (pr-007)

- Модальное окно построено на нативном `<dialog>` с `showModal()`. Браузер сам удерживает фокус внутри окна, делает остальную страницу недоступной (`inert`), закрывает окно по Esc и возвращает фокус на кнопку, которая его открыла. Библиотека для фокус-ловушки не нужна. Окно управляется пропом `open`; закрытие по Esc, кнопкой «Закрыть» или кликом по фону вызывает `onClose`. Прокрутка страницы под открытым окном отключена в CSS (`html:has(dialog[open])`).
- В jsdom у `<dialog>` нет `showModal()` и `close()`, поэтому тесты подставляют минимальную замену в `src/test/setup.ts`.
- `Card` — секция с необязательными заголовком, описанием и действиями. Если заголовок задан, секция подписана им (`aria-labelledby`) и видна дикторам как отдельная область.
- Скелетоны скрыты от экранных дикторов (`aria-hidden`), а о загрузке сообщает контейнер с `role="status"` и скрытым текстом «Загрузка…»: иначе диктор прочитал бы набор пустых блоков.

## Таблицы, пагинация, выпадающие списки (pr-008)

- Выпадающий список — нативный `<select>` со своей стрелкой. На телефонах он открывается системным выбором, а клавиатура и экранные дикторы работают без доработок; кастомный список пришлось бы делать с ролями `combobox` / `listbox` и ручным управлением фокусом. Если понадобится поиск по списку (например, по сортам винограда), для него будет отдельный компонент.
- `DataTable` описывается столбцами: заголовок, функция ячейки и выравнивание. Строки приходят готовыми, поэтому таблица одинаково работает с данными из TanStack Query и из тестов. Подпись (`caption`) скрыта визуально, но обязательна: диктор называет таблицу. Состояния загрузки (скелетоны) и пустого списка встроены. На узком экране таблица прокручивается по горизонтали внутри своей рамки.
- Сортировки в таблице нет: порядок строк будет задавать сервер вместе с постраничной выборкой (pr-014), а сортировка только по загруженной странице вводила бы в заблуждение.
- Пагинация показывает первую и последнюю страницы и окно вокруг текущей; пропуск в одну страницу показывается самой страницей, а не многоточием. Логика расчёта номеров вынесена в `getPageItems` и тестируется отдельно. Текущая страница помечена `aria-current="page"`, на единственной странице панель не рисуется.

## Layout: Header, Sidebar, Footer (pr-009)

- `DashboardTemplate` собирает каркас кабинета: шапка, боковая панель, содержимое, подвал. Страница передаёт только пункты меню и содержимое. Первой в порядке табуляции идёт ссылка «Перейти к содержимому»: клавиатурному пользователю не нужно проходить всё меню на каждой странице.
- Боковая панель на телефоне — выдвижное меню поверх страницы с затемнением, на широком экране (`lg`) — постоянная колонка. Закрытая панель на телефоне скрыта целиком (`hidden`), а не уведена за край экрана, поэтому её ссылки не попадают в порядок табуляции. Закрывается кликом по затемнению, Esc и переходом по ссылке. Кнопка меню в шапке сообщает состояние через `aria-expanded` и связана с панелью через `aria-controls`.
- Состояние панели хранит `useUiStore` из pr-004: шапка и панель — разные компоненты и не должны зависеть друг от друга.
- Пункты меню — обычные ссылки `<a href>`. Маршрутизатор подключится вместе со страницей 404 (pr-010), тогда ссылки заменятся на ссылки маршрутизатора; текущий пункт задаётся полем `current`, а его вычисление по адресу появится вместе с маршрутами.

## Маршрутизация, страница 404 и Error Boundary (pr-010)

- Маршрутизатор — `react-router` (режим data router: `createBrowserRouter` + `RouterProvider`). Маршруты описаны данными в `src/app/routes.tsx`, а не вложенными элементами: так их можно проверять тестами через `createMemoryRouter`, не открывая браузер. Роутер создаётся внутри `App` (`useState`), а не при загрузке модуля, поэтому тесты не зависят от адреса окна.
- Два уровня защиты от ошибок. Корневой маршрут имеет `errorElement`: ошибка отрисовки любой страницы показывает экран «Что-то пошло не так» вместо пустого окна, а шапка и провайдеры остаются работать. Выше стоит `ErrorBoundary` в `AppProviders` — последний рубеж для ошибок вне маршрутов, например в самих провайдерах. Перехватывать ошибки отрисовки умеют только классовые компоненты, поэтому `ErrorBoundary` — единственный класс в проекте.
- `ErrorPage` предлагает «Обновить страницу» (перезагрузка окна): после сбоя состояние компонента неизвестно, а перезагрузка гарантированно его очищает. `ErrorBoundary` принимает функцию запасного экрана с `reset` и необязательный `onError`: туда позже подключится отправка ошибок на сервер (pr-092).
- Страница 404 — маршрут `*`, поэтому любой неизвестный адрес получает одну страницу с понятным текстом и ссылкой на главную.
- Ссылки в шапке и боковом меню заменены на `Link` из `react-router`: переход происходит без перезагрузки страницы. Вычисление текущего пункта меню по адресу появится вместе с первыми страницами кабинета.
- Для production-сборки веб-сервер должен отдавать `index.html` на любой адрес (SPA fallback); в режиме разработки Vite делает это сам.

## Форма входа: React Hook Form + Zod (pr-011)

- Форма — React Hook Form: поля неуправляемые (значения читаются при отправке), поэтому ввод не перерисовывает форму на каждую букву. Правила проверки — схема Zod в `src/schemas/auth.ts`, подключённая через `zodResolver`; та же схема даёт тип значений формы (`z.infer`), так что правила и тип не расходятся. Сообщения об ошибках — по-русски, в схеме.
- У формы `noValidate`: ошибки показывает Zod, а не встроенная проверка браузера на языке системы. Каждая ошибка связана с полем (`aria-invalid`, `aria-describedby` — через `Field` из pr-006), общая ошибка выводится в блоке `role="alert"`.
- При входе пароль только обязателен, его длину и состав не проверяем: правила пароля действуют при регистрации (pr-012), а старый пароль мог быть создан по прежним правилам. Email обрезается по краям.
- Форма не знает про сеть: она принимает функцию `onSubmit` и показывает ошибку, которую та бросила. Текст `ApiError` (поле `detail` ответа сервера, например «Неверный email или пароль») выводится как есть, любая другая ошибка даёт «Не удалось войти». Пока идёт отправка, кнопка заблокирована: двойной клик не отправит запрос дважды.
- Контракт входа, на который рассчитан клиент: `POST /auth/login` с JSON `{ email, password }` возвращает `{ access_token, refresh_token, token_type: "bearer" }`. Это нужно сверить с бэкендом при реализации `/auth/login` (backend/pr-019); если он станет принимать форму `application/x-www-form-urlencoded`, изменится только `src/api/auth.ts`.
- После успешного входа выполняется переход на главную. Сохранение токенов и подстановку их в запросы добавит pr-014, защиту маршрутов — pr-015.
- Для тестов форм добавлен `@testing-library/user-event`: он печатает по символам и нажимает кнопки так же, как пользователь, и ловит ошибки, которых не видно при `fireEvent`.
- `AuthTemplate` — общий каркас страниц входа, регистрации и восстановления пароля (pr-012, pr-013). Ссылки на них из формы входа появятся вместе с этими страницами.

## Форма регистрации с выбором роли (pr-012)

- Выбрать при регистрации можно «Виноградарь» (`user`) и «Агроном» (`agronomist`); роли администратора в списке нет, а схема Zod её отклоняет. Администратора назначает только администратор: иначе любой мог бы выдать себе все права. Роль агронома даёт право подтверждать диагнозы (pr-052), поэтому сервер не должен слепо доверять самостоятельному выбору — подтверждение агронома администратором решается в ролевой модели (backend/pr-022). Форма отправляет выбранную роль как заявленную.
- Правила пароля: от 8 до 128 символов, хотя бы одна буква (любого алфавита, `\p{L}`) и одна цифра. Минимум 8 символов и отсутствие «только цифры» отсекают самые слабые пароли без требований вроде спецсимволов, которые лишь подталкивают к предсказуемым заменам. Верхняя граница нужна, потому что хэширование Argon2 (pr-016) на очень длинной строке — лёгкая нагрузка на сервер. Те же правила должен проверять бэкенд (pr-018): проверка в форме — удобство для пользователя, а не защита.
- Подтверждение пароля проверяется схемой (`refine` с ошибкой у поля подтверждения) и серверу не отправляется: `register()` отправляет только email, пароль, имя и роль. Поля пароля помечены `autocomplete="new-password"`, поэтому менеджер паролей предлагает сгенерировать и сохранить новый, а не подставляет старый.
- Занятый email (ответ 409) показывается у поля email собственным текстом, а не общей ошибкой формы: пользователь сразу видит, что менять. Любая другая ошибка сервера выводится блоком над кнопкой.
- После регистрации выполняется переход на страницу входа с сообщением «Аккаунт создан»: сообщение передаётся в состоянии маршрута и пропадает при обновлении страницы. Автоматический вход после регистрации не делается: токены сохраняет отдельный модуль (pr-014), а вход всё равно подтверждает, что пользователь знает пароль.
- Контракт, на который рассчитан клиент: `POST /auth/register` с JSON `{ email, password, full_name, role }` возвращает созданного пользователя `{ id, email, full_name, role }` с кодом 201, а занятый email — код 409. Сверить с бэкендом при реализации `/auth/register` (backend/pr-018).
- Страницы входа и регистрации ссылаются друг на друга; общий каркас — `AuthTemplate`, у него появилось место для нижней ссылки.

## Восстановление пароля (pr-013)

- Восстановление — два шага на двух страницах. `/forgot-password`: пользователь вводит email и получает письмо со ссылкой. `/reset-password?token=…`: по ссылке из письма задаётся новый пароль. Ключ берётся из адреса страницы; без него страница объясняет, что ссылка неполная, и предлагает запросить новую. Ключ не показывается на экране и не сохраняется.
- После запроса страница пишет «Если аккаунт с адресом … существует, мы отправили письмо» и не подтверждает, что аккаунт есть. Сервер отвечает одинаково для любого адреса: иначе форма позволяла бы перебором узнавать, какие email зарегистрированы. Тот же приём должен соблюдать бэкенд (backend/pr-024).
- Правила нового пароля вынесены в одну схему и общие для регистрации и сброса: пароль, допустимый при регистрации, нельзя нарушить при смене. Поля помечены `autocomplete="new-password"`.
- Ошибка сервера при установке пароля (например, «Ссылка устарела») показывается как есть, рядом остаётся ссылка «Запросить новую ссылку»: пользователь не оказывается в тупике. После успешной смены переход на вход с сообщением «Пароль изменён»; автоматический вход не делается, пока токены не сохраняются модулем из pr-014.
- Страница входа получила ссылку «Забыли пароль?»; сообщения «Аккаунт создан» и «Пароль изменён» передаются состоянием маршрута, поэтому исчезают при обновлении страницы.
- Контракт, на который рассчитан клиент (сверить с бэкендом в backend/pr-024): `POST /auth/password-reset` с `{ email }` отвечает 202 всегда; `POST /auth/password-reset/confirm` с `{ token, new_password }` отвечает 204, а при неверном или устаревшем ключе — 400 с текстом в `detail`.

## Хранение JWT-токенов: Secure Cookie, а не LocalStorage (pr-014)

- Выбор из roadmap «Secure Cookie / LocalStorage» сделан так: **access-токен хранится только в памяти** (хранилище Zustand без `persist`), **refresh-токен — в `HttpOnly`-cookie, которую выставляет сервер**. Из `localStorage` токен может прочитать любой скрипт на странице: одна XSS-уязвимость или скомпрометированная зависимость — и долгоживущий токен украден. `HttpOnly`-cookie для скриптов недоступна совсем, а access-токен в памяти живёт недолго (время жизни задаёт сервер, порядка 15 минут) и пропадает при закрытии вкладки.
- Цена решения — после перезагрузки страницы access-токена в памяти нет. Поэтому при запуске (`initSession`) приложение запрашивает новый токен у `POST /auth/refresh`: браузер сам прикладывает cookie. Пока ответа нет, состояние сессии — `unknown`, и страницы, зависящие от входа, подождут (защищённые маршруты, pr-015). Если cookie нет или она недействительна, пользователь анонимен.
- Обновление токена при 401: если запрос к API вернул 401, приложение один раз обновляет токен и повторяет запрос. Одновременные 401 делят один запрос на обновление: при ротации refresh-токенов второй параллельный запрос получил бы отказ и разлогинил пользователя. Повтор делается один раз (`_retried`), поэтому постоянный 401 не приводит к циклу. Запросы к `/auth/*` не повторяются: неверный пароль или устаревший refresh не лечатся обновлением.
- Выход (`useLogout`) очищает сессию в любом случае, даже если сервер не ответил: токен в памяти нельзя оставлять, а cookie перестанет действовать по таймеру. Сервер при выходе должен отозвать refresh-токен (в таблице `refresh_tokens` есть `revoked_at`) и удалить cookie.
- Запросы идут с `withCredentials`: так cookie отправляется и когда API находится на другом адресе (в разработке с `VITE_API_URL`). Обычно фронтенд и API работают с одного адреса (в разработке — через прокси Vite), тогда это ничего не меняет.
- **Требования к бэкенду (backend/pr-017, pr-019, pr-020).** `POST /auth/login` и `POST /auth/refresh` возвращают `{ access_token, token_type: "bearer" }` и выставляют cookie `refresh_token` с флагами `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`; `refresh` читает cookie, ротирует её и при недействительной отвечает 401; `POST /auth/logout` отзывает токен, удаляет cookie и отвечает 204. Узкий `Path` не даёт браузеру отправлять refresh-cookie с остальными запросами, а `SameSite=Strict` защищает от CSRF: чужой сайт не сможет заставить браузер отправить её. Это меняет контракт из pr-011: в теле ответа входа больше нет `refresh_token`.
- В локальной разработке по `http://127.0.0.1` флаг `Secure` работает: браузеры считают `localhost` и `127.0.0.1` безопасным контекстом.

## Защищённые маршруты (pr-015)

- Два охранника маршрутов в `src/app/guards.tsx`: `ProtectedRoute` пускает только вошедших, `GuestRoute` — только гостей. Они вложены в описание маршрутов как «родитель без пути»: новые страницы кабинета достаточно добавить в `children` защищённого маршрута. Страница 404 и ссылка сброса пароля (`/reset-password`) открыты всем: по ссылке из письма приходят и вошедшие, и гости.
- Три состояния сессии определяют поведение. Пока сессия восстанавливается после загрузки страницы (`unknown`, pr-014), показывается экран загрузки: без него вошедшего пользователя на мгновение перекинуло бы на страницу входа, а затем обратно. Гость (`anonymous`) уходит на `/login`, вошедший (`authenticated`) со страниц входа и регистрации — на главную.
- Возврат после входа: охранник запоминает адрес (`pathname` и строку запроса) в состоянии маршрута, и после входа пользователь попадает именно туда. Переход выполняет `GuestRoute`, как только хранилище сессии стало «вошедшим»: так не нужен второй механизм перехода в самой странице входа, и вошедший пользователь, открывший `/login` вручную, уходит оттуда так же.
- Адрес возврата проверяется: допускается только путь внутри приложения (начинается с `/`, но не с `//`). Иначе значение вида `//чужой.сайт` превратило бы страницу входа в способ отправить пользователя на чужой сайт (open redirect). Состояние маршрута ставит только наш код, но проверка стоит дёшево и защищает от ошибки в будущем.
- Главная страница закрыта: приложение — личный кабинет, ему нечего показывать гостю. Добавлена кнопка «Выйти» (`useLogout`): без неё вошедший не мог бы закончить сессию.
- Охранники проверяют только факт входа. Доступ по ролям (администратор, агроном, виноградарь) — ролевая модель бэкенда (backend/pr-022); интерфейс будет скрывать недоступные разделы, но защитой остаётся проверка на сервере: скрытая кнопка не мешает отправить запрос вручную.
- В тестах по умолчанию пользователь не вошёл (`src/test/setup.ts`), а тесты, которым нужна сессия, задают её явно.

## Переключатель языков RU, RO, EN (pr-016)

- Переводы на i18next с `react-i18next`. Тексты лежат в `src/i18n/locales/` в виде TypeScript-объектов, а не JSON: словари `ro` и `en` типизированы по форме русского (`Messages`), поэтому пропущенный или лишний ключ — ошибка компиляции, а не пустое место в интерфейсе. Словари маленькие и входят в основной бандл; загрузка по требованию понадобится, только если они заметно вырастут.
- Язык выбирается в порядке: сохранённый выбор пользователя (`localStorage`, ключ `vitiguard.language`), затем язык браузера, иначе русский. Региональные варианты сводятся к поддерживаемым (`ro-MD` → `ro`, `en-GB` → `en`).
- При смене языка обновляется `<html lang>`: от него зависят произношение у экранных дикторов, переносы и проверка орфографии.
- Переключатель — обычный `<select>` с невидимой подписью «Язык»; он есть в шапке кабинета и на страницах входа. Названия языков написаны на самих языках («Română», «English»): человек, не читающий текущий язык, всё равно найдёт свой.
- Сообщения валидации в Zod-схемах — ключи перевода (`validation.*`), а текст подставляет `Field`. Схемы создаются один раз при загрузке модуля, и готовый текст в них остался бы на языке запуска. Ошибки сервера `Field` показывает как есть.
- Фразы со ссылкой или выделением внутри переводятся целиком через `Trans`: порядок слов в румынском и английском другой, и склейка фразы из кусков дала бы неправильный текст. Теги внутри перевода названы не как HTML-элементы (`<request>`, а не `<link>`): парсер i18next считает `link` пустым элементом и выбрасывает текст ссылки.
- Ограничение: тексты ошибок, которые присылает бэкенд (например, «Неверный email или пароль»), пока приходят на русском. Сервер будет учитывать заголовок `Accept-Language` отдельной задачей; до тех пор фронтенд переводит только свои сообщения.
- Тесты проверяют тексты по-русски: `src/test/setup.ts` перед каждым тестом очищает `localStorage` и включает русский язык.

## Тёмная и светлая тема (pr-017)

- Три режима: «как в системе» (по умолчанию), «светлая», «тёмная». Выбор хранится в `localStorage` (`vitiguard.theme`); в режиме системы тема меняется вместе с настройкой ОС без перезагрузки страницы.
- Тёмная тема включается классом `dark` на `<html>` (`@custom-variant dark` в Tailwind 4), а не только медиазапросом `prefers-color-scheme`: иначе нельзя было бы выбрать тему вручную.
- Компоненты используют смысловые цвета вместо оттенков палитры: `canvas` и `surface` — фон страницы и карточек, `ink*` — текст по степени важности, `line*` — границы, `accent`, `accent-soft`, `danger`. Значения — CSS-переменные в `src/index.css`, тема переопределяет только их. Без этого каждый элемент получил бы пару классов `bg-white dark:bg-stone-900`, и новая разметка легко забывала бы вторую половину.
- Тёмные оттенки подобраны с контрастом текста не ниже 4.5:1 (WCAG AA). Основные кнопки (`emerald-700`, `red-700` с белым текстом) одинаковы в обеих темах: на них контраст достаточный и так. `color-scheme` переключает и встроенные элементы браузера — полосы прокрутки, выпадающие списки, автозаполнение.
- Тема применяется маленьким скриптом в `index.html` ещё до загрузки приложения. Без него тёмная тема на мгновение показывалась бы светлой («вспышка») — пока загружается и запускается JavaScript.
- Переключатель — `<select>` рядом с выбором языка, в шапке кабинета и на страницах входа.

## Юнит-тесты базовых UI-компонентов (pr-018)

- В roadmap указан Jest, но тесты с первого PR пишутся на Vitest: у него тот же API (`describe`, `it`, `expect`, моки), а сборка и алиасы берутся из конфигурации Vite, без отдельной настройки Babel или ts-jest. React Testing Library и `jest-dom` работают с ним без изменений.
- Тесты проверяют поведение, видимое пользователю: роли, подписи, тексты, реакцию на клики и клавиши. Классы проверяются только там, где они и есть поведение (скрытая панель, переопределение стилей кнопки).
- Добавлены тесты для компонентов, которые до этого проверялись только через страницы: формы восстановления и смены пароля, шаблоны, экран загрузки, скелетон и спиннер, а также крайние случаи пагинации, таблицы, боковой панели и темы.
- Покрытие измеряется в CI (`npm run test:coverage`, `@vitest/coverage-v8`). Пороги: 95% строк и функций и 90% ветвлений по проекту, для `src/components` — 100% строк и функций и 95% ветвлений: базовые компоненты используются на всех страницах, и ошибка в них видна везде. Падение покрытия ниже порога валит проверку PR.
- Отчёт в HTML складывается в `coverage/` (не попадает в репозиторий).

## Подключение карты (pr-019)

- Выбор из roadmap «Mapbox GL / Leaflet» — **MapLibre GL JS**, открытое продолжение Mapbox GL JS. С Mapbox GL у него общий API и формат стилей, но нет обязательного ключа доступа и платы за загрузки карты. Leaflet проще, но рисует растровые тайлы через DOM и хуже справляется с тысячами полигонов участков и векторными слоями, которые понадобятся для индексов и рисков. Версия зафиксирована точно (6.11.2): обновление карты — отдельное решение.
- Подложка пока одна — растровая схема OpenStreetMap: без ключа, с открытой лицензией; атрибуция «© OpenStreetMap» обязательна и показывается в углу карты. Спутник и гибрид — следующая задача (pr-020).
- При открытии карта вписывает Молдову целиком в любой экран (`bounds`), а увести её дальше рамки с запасом вокруг страны нельзя (`maxBounds`). Минимальный масштаб — 6, максимальный — 19 (уровень отдельных рядов виноградника).
- Код карты загружается отдельным файлом, только когда пользователь открыл `/map` (`lazy` в маршруте): MapLibre весит больше всего остального приложения, и на страницах входа он не нужен. Пока файл загружается при первом открытии, показывается экран загрузки (`hydrateFallbackElement`).
- MapLibre разбирает тайлы в фоновом потоке (Web Worker). Сам он ищет файл потока рядом со своим кодом, а Vite складывает сборку иначе, поэтому адрес собранного потока передаётся явно (`setWorkerUrl` с импортом `?worker&url`); поток собирается как ES-модуль. Проверено в браузере и в режиме разработки, и на собранной версии.
- Без WebGL карта не может работать; это проверяется до создания карты, и вместо пустого блока пользователь видит объяснение.
- Подсказки кнопок карты переведены (RU, RO, EN). MapLibre принимает их только при создании карты, поэтому при смене языка карта пересоздаётся. Язык меняют редко, а всё, что показано на карте, берётся из данных приложения.
- В тестах (jsdom без WebGL) MapLibre заменён заглушкой (`src/test/maplibre.ts`), которая запоминает настройки карты: тесты проверяют, что карта создаётся с нужными границами, кнопками и подписями и удаляется при уходе со страницы.
- В кабинете появились разделы «Главная» и «Карта» (`useNavItems`), кнопка выхода вынесена в отдельный компонент и стоит в шапке.

## Подложки: схема, спутник, гибрид (pr-020)

- Три подложки: «схема» — OpenStreetMap, «спутник» — снимки Esri World Imagery, «гибрид» — те же снимки с дорогами (Esri World Transportation) и подписями населённых пунктов и границами (Esri World Boundaries and Places). Сервисы Esri доступны без ключа при обязательной атрибуции; MapLibre показывает атрибуцию только видимых источников, поэтому подпись в углу меняется вместе с подложкой.
- Все подложки лежат в одном стиле карты, а переключение меняет только видимость слоёв (`setLayoutProperty`). Замена стиля через `setStyle` удалила бы вместе с подложкой и слои, которые приложение добавит поверх: участки, индексы, риски. Видимость для каждой подложки описана в одном месте (`src/lib/basemaps.ts`) и проверяется тестами.
- У снимков `maxzoom` источника — 18: глубже снимки есть не везде, и на крупных масштабах карта увеличивает последний доступный уровень вместо пустых тайлов.
- Выбранная подложка сохраняется в `localStorage` (`vitiguard.basemap`): тот, кто работает по снимкам, не переключает её при каждом открытии карты. По умолчанию — схема: она легче и быстрее загружается на мобильном интернете.
- Переключатель — группа радиокнопок, оформленная как сегментированная кнопка в углу карты: браузер сам даёт переход стрелками и озвучивание выбранного варианта.
- Если выбор сделан раньше, чем загрузился стиль, он применяется по событию `style.load`.
- Тестам дан запас по времени (`testTimeout` — 15 секунд): формы проверяются набором текста через user-event, и под нагрузкой с измерением покрытия пяти секунд по умолчанию изредка не хватало.

## Границы Молдовы и районов (pr-021)

- Источник — geoBoundaries (gbOpen, уровень ADM1, CC BY 3.0 IGO; исходные данные UNHCR и OCHA): 37 единиц — 32 района, муниципии Кишинёв, Бельцы и Бендеры, АТО Гагаузия и АТЕ Левобережья Днестра. Атрибуция показывается в углу карты.
- Данные подготовлены скриптом `scripts/build_districts.py` и лежат статическим файлом `public/geo/moldova-districts.geojson` (155 КБ, около 45 КБ при сжатии): границы меняются редко, и отдельный запрос к API ради них не нужен. Скрипт исправляет названия (в исходнике они без диакритики и с ошибками: «RIscani», «SIngerei») на официальные румынские, округляет координаты до четырёх знаков (около 10 м) и строит границу страны объединением районов — так линии страны и районов совпадают точно.
- У районов, состоящих из нескольких частей (Criuleni, Dubăsari, Găgăuzia и другие), MapLibre подписал бы каждую часть. Поэтому в файле есть отдельная точка подписи для каждого района — внутри самой большой его части.
- Слои границ и подписей лежат в том же стиле над подложками и видны на любой из них. Цвет — фиолетовый из логотипа: он заметен и на схеме, и на снимках. Подписи районов появляются с масштаба 7: при меньшем 37 подписей сливаются.
- Для подписей MapLibre нужны шрифты в формате глифов. Шрифт Open Sans Semibold (открытая лицензия) лежит в `public/fonts`: три диапазона — латиница, румынские ă, î (256–511) и ș, ț (512–767). Свой сервер шрифтов не нужен, и карта не зависит от демонстрационного сервера MapLibre.
- Адреса данных и шрифтов абсолютные. MapLibre загружает их в фоновом потоке, запущенном из blob-адреса, и относительный путь там не указывает на наш сайт.
- GeoJSON исключён из Prettier: форматирование почти вдвое раздувало минифицированный файл.
- Карта проверена в браузере на собранной версии для всех трёх подложек.

## Рисование полигона участка (pr-022)

- В roadmap указан Mapbox Draw, но он написан под Mapbox GL и с MapLibre работает только с правками CSS-классов и типов. Вместо него — **Terra Draw** (MIT): библиотека не привязана к конкретной карте, у неё официальный адаптер для MapLibre, встроенные типы TypeScript и проверки контура. Версии зафиксированы точно (terra-draw 1.35.0, адаптер 1.4.1), как и у MapLibre.
- Сценарий: кнопка «Нарисовать участок» → клики по углам → замыкание кликом по первой точке или Enter (Esc отменяет). После завершения контур сразу переходит в режим правки: вершины перетаскиваются, белые точки на сторонах добавляют новые углы. Пока что на карте один черновой контур; сохранение — следующая задача (pr-023).
- Самопересекающийся контур («восьмёрка») не завершается: у него нет осмысленной площади, и бэкенд его тоже не примет.
- Площадь считается на клиенте, сразу при рисовании и правке, по формуле площади многоугольника на сфере (Chamberlain, Duquette, JPL, 2007) со средним радиусом Земли — как в Turf. Тест сверяет результат с Turf на эталонном контуре. Отдельная библиотека ради одной функции не нужна. Окончательную площадь участка сохраняет бэкенд (PostGIS); на широте Молдовы расхождение — доли процента.
- Площадь показывается в гектарах, в формате чисел текущего языка. Строка с площадью — `aria-live`: при правке контура экранный диктор сообщает новое значение.
- Элементы поверх карты получают загруженную карту через контекст (`MapContext`, `useMap`) и появляются только после загрузки стиля: Terra Draw добавляет свои слои в стиль и раньше не может.
- Ограничение: рисование работает мышью и касанием. Ввод контура с клавиатуры (по координатам) — в форме участка.
- Проверено в браузере на собранной версии: контур рисуется реальными кликами, переходит в режим правки, площадь выводится.

## Форма участка при рисовании (pr-023)

- Когда контур замкнут, под ним появляется форма: площадь, подсказка по правке контура, название участка и кнопки «Сохранить участок» и «Удалить контур». Контур можно править и после того, как название введено: площадь в форме пересчитывается.
- Форма (`VineyardForm`) общая для нового участка и правки существующего — различаются начальные значения и подпись кнопки. Хуки `useCreateVineyard` и `useUpdateVineyard` после успеха сбрасывают кэш списка участков, чтобы участки на карте (pr-024) обновились сами.
- Контур с карты — один `Polygon`; серверу уходит `MultiPolygon` из одной части (`toMultiPolygon`): в базе участок всегда `MultiPolygon` (backend/pr-026).
- Панель рисования не знает о форме: она отдаёт готовый контур, площадь и функцию сброса в `renderDrawn`, а страница карты решает, что показать. Так та же панель подойдёт и для правки участка.
- Сброс контура передаётся наружу, поэтому сам рефов не читает (так требует React Compiler): он меняет состояние, а Terra Draw очищает эффект. В этом эффекте контур сначала забывается, а потом удаляется с карты. Перед удалением Terra Draw снимает с контура выделение и сообщает об этом как об изменении; при обратном порядке панель приняла бы это за правку и стёрла бы сообщение «Участок сохранён». Ошибку нашла проверка в браузере, теперь её ловит тест.
- После сохранения контур убирается с карты, а над картой появляется «Участок «…» сохранён» (`role="status"`, озвучивается экранными дикторами). Ошибка сервера показывается в форме, контур остаётся на карте: нарисованное не теряется.
- Заглушка Terra Draw для тестов вынесена в `src/test/terraDraw.ts` и подключена глобально, как заглушка MapLibre: сквозной тест страницы карты проходит путь «карта загрузилась → контур нарисован → название введено → участок сохранён».
- Проверено в браузере с настоящим бэкендом: участок сохраняется в PostGIS как `MULTIPOLYGON`, площадь по PostGIS (эллипсоид) отличается от расчёта на клиенте на 0,27 %.

## Участки пользователя на карте (pr-024)

- Участки показываются слоем поверх подложки и границ: полупрозрачная заливка, контур и подпись с названием (с масштаба 12 — мельче участок занимает несколько пикселей, и подпись закрыла бы соседей). Цвет тот же, что у рисуемого контура.
- Данные берутся из `GET /api/v1/vineyards` (backend/pr-027) через TanStack Query. Карте нужны все участки сразу, поэтому страницы по 100 загружаются подряд; у виноградаря их единицы или десятки, и обычно хватает одного запроса. После сохранения нового участка кэш сбрасывается (pr-023), и он появляется на карте без перезагрузки страницы.
- При первом открытии карта один раз приближается к участкам (`fitBounds`, не крупнее масштаба 15): участок в пару гектаров на масштабе всей страны занимает меньше пикселя. Новые участки карту не двигают — пользователь остаётся там, где рисовал. Если участков нет, карта показывает всю Молдову.
- id участка лежит в свойствах объекта, а не в его `id`: MapLibre принимает там только числа, а у участков UUID. Попапы и выбор участка (pr-026) возьмут id из свойств.
- Источник и слои удаляются при уходе со страницы. Если карту к этому моменту уже удалил `MapView`, удалять нечего, и ошибка не нужна.
- Проверено в браузере с настоящим бэкендом: сохранённый участок остаётся на карте, после повторного открытия карта приближается к нему.

## Тултипы и попапы участков (pr-026)

- Наведение на участок — подсказка с названием и курсор-«рука»; клик — попап с названием, площадью и датой добавления. Площадь в попапе — серверная (`area_ha`, backend/pr-029), а не клиентский расчёт при рисовании.
- Подсказка и попап — `Popup` из MapLibre: они двигаются вместе с картой и сами выбирают сторону, чтобы не выйти за край. Содержимое попапа рисует React через портал в контейнер попапа, поэтому оно переводится, форматирует числа и даты по языку и оформляется классами приложения. Закрыть попап можно крестиком (подпись переведена), кликом мимо или Esc.
- Попапы MapLibre по умолчанию белые; цвета взяты из переменных темы. Стили MapLibre загружаются позже (вместе с кодом карты), поэтому селекторы на уровень точнее.
- Пока рисуется или правится контур, участки не реагируют на наведение и клики: клик в это время ставит точку контура, а не выбирает участок. Флаг `isDrawing` — в хранилище карты, его включает и выключает панель рисования.
- Цветовая индикация по уровню риска (pr-025) выполняется после того, как бэкенд начнёт считать риски (модуль прогноза, спринт 5): без данных о рисках раскрашивать нечего.
- Проверено в браузере с настоящим бэкендом: попап открывается по клику, площадь и дата — с сервера, в тёмной теме читается.

## Поиск по названию и координатам (pr-028)

- Поле поиска — в панели инструментов карты над кнопкой рисования. Оно ищет по своим участкам (часть названия, без учёта регистра) и понимает координаты: «47.1405, 28.861», «47.1405,28.861», «47.1405 28.861», «47,1405; 28,861» — в порядке «широта, долгота», как их копируют из Google и Яндекс Карт. Запятая бывает и десятичной, и разделителем; в каждом числе не больше одной дробной части, поэтому разбор однозначен.
- Поиск по участкам идёт на клиенте по уже загруженному списку (pr-024): участков у пользователя единицы и десятки, и запрос к серверу на каждую букву не нужен. Поиск по адресам и населённым пунктам (геокодинг) не делается: подписи сёл есть на подложке, а внешний сервис геокодинга — лишняя зависимость.
- Выбор участка приближает к нему карту и открывает его попап. Выбранный участок перенесён из `VineyardPopups` в хранилище карты (`selection`), чтобы его могли выбрать и клик по карте, и поиск. Переход к координатам ставит метку и переносит карту на масштаб 15; новая метка заменяет прежнюю.
- Поле — комбобокс по шаблону WAI-ARIA: фокус остаётся в поле, варианты перебираются стрелками (по кругу), Enter выбирает, первый Esc закрывает список, второй очищает поле. Текущий вариант диктор узнаёт из `aria-activedescendant`. Число результатов отдельно не озвучивается: у языков разные формы множественного числа, а список и так читается.
- Проверено в браузере с настоящим бэкендом: участок находится по названию и открывается его попап, по координатам Триумфальной арки метка встаёт на арку.

## Измерение расстояний и площадей (pr-029)

- Кнопка «Измерить расстояние и площадь» включает линейку: клики ставят точки, панель показывает длину ломаной, а с трёх точек — и площадь замкнутой фигуры (в гектарах и квадратных метрах). «Убрать точку» снимает последнюю, «Готово» или Esc выключают линейку. Сценарий — прикинуть ширину междурядья или площадь куртины, не создавая участок.
- Линейка — свои обработчики кликов и слой GeoJSON, а не второй экземпляр Terra Draw: два рисующих инструмента на одной карте перехватывали бы события друг у друга. Пока работает линейка, рисование участка недоступно, и наоборот; общий флаг `isDrawing` в хранилище карты заодно отключает попапы участков.
- Длина — формула гаверсинусов, площадь — та же сферическая формула, что при рисовании участка (pr-022), обе со средним радиусом Земли. Тест сверяет длину градуса меридиана с расчётом 2πR/360.
- Пока линейка включена, двойной клик ставит точки, а не приближает карту, курсор — прицел. Цвет линейки — янтарный, чтобы её не путали с участками (изумрудный) и границами районов (фиолетовый).
- Элементы поверх карты теперь появляются по событию `style.load`, а не `load`. `load` ждёт загрузки всех тайлов первого экрана, и при медленном тайловом сервере поиск, рисование и линейка появлялись с большой задержкой (это видно при проверке в браузере). Слоям и рисованию нужен только загруженный стиль.
- Проверено в браузере: точки ставятся кликами, расстояние и площадь считаются, кнопка рисования на это время отключена.

## Фильтры участков, сорт и год посадки (pr-027)

- В форме участка появились сорт (выбор из справочника, backend/pr-034) и год посадки (от 1900 до текущего года, как проверяет бэкенд); оба поля необязательны. В карточке участка на карте показываются сорт и год посадки.
- Панель фильтров на карте: сорт (только те сорта, что есть у участков пользователя, и «Без сорта») и площадь «от — до» в гектарах. Подпись «Показано N из M» озвучивается при каждом изменении. Фильтр по статусу (уровню риска) появится вместе с расчётом рисков на бэкенде.
- Фильтр работает на клиенте по уже загруженному списку участков: их у пользователя десятки, и запрос к серверу на каждое изменение не нужен. Он хранится в хранилище карты и применяется к слою участков; приближение карты к участкам при первом открытии от фильтра не зависит.
- Поля площади хранят текст как набран, а в фильтр уходит разобранное число: иначе при вводе «1,» запятая сразу пропадала бы. Принимается и запятая, и точка; отрицательная площадь становится нулём.
- Справочник сортов кэшируется на 10 минут: агроном меняет его редко.

## Фирменный стиль по логотипу

- Логотип: эмблема (лист лозы, щит с сетью и стрелкой роста, гроздь из десяти ягод) и надпись «VitiGuard» с подписью «MD | Vineyard health monitoring system». Эмблема взята из исходного макета: фон удалён, полупрозрачные края очищены от примеси белого, чтобы на тёмной теме не было светлой каймы (`src/assets/emblem.png`). Надпись набрана текстом, а не картинкой: она остаётся чёткой на любом экране и перекрашивается в тёмной теме — тёмно-фиолетовые буквы макета на тёмном фоне были бы не видны.
- Шрифт надписи и заголовков страниц — Montserrat (OFL, пакет `@fontsource-variable/montserrat`, хранится вместе с приложением, без запросов к внешнему серверу шрифтов); основной текст остаётся системным шрифтом — он быстрее и привычнее для форм.
- Палитра `brand` снята с логотипа: ягоды от `#622ac3` до `#a68af0`, надпись `#351578`. Акцентный цвет интерфейса (кнопки, ссылки, выбранная подложка, фокус) — фиолетовый вместо зелёного. Белый текст на кнопке `brand-700` — контраст около 8:1. Участки на карте остаются изумрудными: зелёный там обозначает растительность, а не фирменный цвет; границы районов перекрашены в фирменный фиолетовый.
- Анимации короткие и ненавязчивые: карточка входа и содержимое кабинета появляются подъёмом (0,4 с), логотип на крупных экранах — увеличением, на экране загрузки эмблема «дышит». Все анимации — через `motion-safe`: у пользователей с настройкой «уменьшить движение» их нет. Кнопки слегка «нажимаются» и получают тень при наведении.
- Иконки вкладки и ярлыка на телефоне (`favicon.png`, `apple-touch-icon.png`) — эмблема; цвет панели браузера на телефоне — фирменный (`theme-color`).

## Виноградники OpenStreetMap на карте (pr-034)

- Справочный слой виноградников Молдовы из OpenStreetMap (backend/pr-033) включается флажком «Виноградники OpenStreetMap» в панели карты. Он показывает, где в округе уже есть виноградники, и помогает обвести свой участок по готовому контуру.
- Вместо кластеризации из плана — загрузка по окну карты: полигонов около 17 тысяч, и все сразу браузеру не нужны. Слой запрашивает только видимое окно и только с масштаба 12 (на более мелком масштабе виноградник — пара пикселей, а сервер не принимает окно больше 1°). На мелком масштабе под флажком подсказка «Приблизьте карту», она же озвучивается экранным диктором.
- Окно округляется наружу до 0,01° (около километра), поэтому мелкие сдвиги карты дают тот же запрос, и ответ берётся из кэша TanStack Query (10 минут). Пока грузится новое окно, на карте остаются полигоны предыдущего — слой не мигает.
- Слой светлее и тоньше участков пользователя (лавандовая заливка 18 % и пунктирный контур фирменного фиолетового) и лежит под ними: это подсказка, а не данные пользователя.
- Пока флажок выключен, ни источник, ни запросы к серверу не создаются.

## Диагностика по фото листа (pr-036, pr-039, pr-040, pr-043)

- Раздел «Диагностика» (`/diagnosis`) — загрузка фото листа и ответ модели с сервера (`POST /api/v1/ai/diagnose`, backend/pr-044). Ссылка — в меню кабинета и на главной.
- Фото выбирается перетаскиванием или через диалог выбора файла; на телефоне тот же диалог предлагает камеру. Атрибут `capture` не используется: он запретил бы выбрать уже снятое фото из галереи.
- Формат (JPEG, PNG, WebP) и размер (до 10 МБ) проверяются ещё на клиенте — те же ограничения, что на сервере: заведомо неподходящий файл не уходит в сеть, а причина видна сразу. Серверная проверка остаётся главной.
- Предпросмотр — ссылка `blob:` на выбранный файл; она освобождается при смене фото и уходе со страницы, иначе файл оставался бы в памяти вкладки.
- Пока идёт анализ, кнопка заблокирована и показывает индикатор, а в карточке результата — «Анализируем фото…». Время ожидания запроса увеличено до минуты: первый запрос после запуска сервера ещё и загружает модель.
- Результат: диагноз (здоровый лист — зелёным, как растительность на карте; болезнь — красным), уверенность и вероятности всех шести классов полосами по убыванию. Числа в процентах форматируются по языку интерфейса; полосы скрыты от экранного диктора, потому что дублируют числа.
- При флаге сервера `low_confidence` показывается предупреждение с советом переснять лист, а под результатом — оговорка, что это подсказка, а не заключение агронома: на полевых снимках модель ошибается заметно чаще, чем на лабораторных (ml/pr-010).
- Новое фото сбрасывает результат прежнего, чтобы диагноз не оказался рядом с чужим снимком.

## Панель инструментов карты не закрывает участки (pr-034, доработка)

- Панель поверх карты (поиск, рисование, измерение, фильтры, слой OpenStreetMap) выросла и закрывала левую часть карты вместе с участками, а на невысоких экранах её низ обрезался. Панель вынесена в компонент `MapToolbar`: она уже (16rem), прокручивается, если не помещается по высоте, и скрывается целиком кнопкой «Скрыть панель» — на её месте остаётся кнопка «Инструменты».
- Фильтры и слой OpenStreetMap нужны реже остальных инструментов, поэтому свёрнуты в блок «Фильтры и слои» (`<details>`: раскрывается с клавиатуры и озвучивается без дополнительной разметки). Если фильтр включён, блок открыт сразу: иначе было бы непонятно, куда делись участки.
- При первом показе карта приближается к участкам с отступом слева под ширину панели, чтобы участки не оказались под ней; на узкой карте (меньше трёх ширин панели) отступ обычный.

## Тепловая карта и маска поражения на странице диагностики (pr-041, pr-042)

- После диагноза под фото появляется карточка «Где модель увидела болезнь»: фото с наложением и переключатель «Тепловая карта / Поражение / Только фото». Наложения приходят с сервера (backend/pr-046, pr-047) прозрачными PNG в пропорциях фото, поэтому картинка той же ширины ложится поверх фото без пересчёта координат. Карточка стоит слева, под фото: справа и так длинный список вероятностей.
- Для маски показывается доля поражённой площади листа с пометкой «ориентировочно»: U-Net училась на автоматической разметке OpenCV и иногда принимает тень или черешок за поражение. Если сервер не вернул наложение (модели нет), соответствующей кнопки нет; если нет обоих, карточка не показывается.
- Переключатель-радиогруппа из подложек карты вынесен в общий компонент `SegmentedControl`; ссылка `blob:` на выбранный файл — в хук `useObjectUrl` (освобождается при смене файла и уходе со страницы).

## Статистика по районам (часть pr-053)

- Раздел «Районы» (`/regions`) показывает сводку `GET /api/v1/regions/stats` (backend/pr-036): сколько виноградников размечено в OpenStreetMap и их площадь по всей стране, участки пользователя, график десяти районов с наибольшей площадью виноградников и таблицу всех 37 районов.
- Таблица сортируется по любому столбцу (по умолчанию — по площади виноградников, по убыванию). Сортировка добавлена в общий `DataTable`: столбец с `sortValue` получает кнопку в заголовке и `aria-sort`, строки сравниваются по правилам языка интерфейса (`localeCompare`), поэтому «Bălți» стоит рядом с «Basarabeasca», а не в конце.
- Под таблицей — источник и оговорка: OpenStreetMap размечен не полностью, и реальная площадь виноградников больше.
- Создание и изменение участка обновляют и сводку по районам: в ней есть участки пользователя.
- Ссылки на раздел — в меню кабинета и на главной.

## Карточка участка: район, погода, окрестности, скачивание и удаление (pr-054)

- Попап участка на карте вынесен в компонент `VineyardCard`. Кроме площади, сорта и года посадки в нём теперь район (из контекста участка, backend/pr-036), погода сейчас (`/weather/current`, Open-Meteo) и окрестности по OpenStreetMap: сколько виноградников в радиусе 1 км, расстояние до ближайшего и доля участка, совпадающая с разметкой OSM (backend/pr-033). Соседние виноградники важны для риска: споры милдью и оидиума переносятся ветром.
- Погода берётся в точке клика, округлённой до 0,01° (около километра): погода по участку одна, и повторный клик по нему же или по соседнему участку берёт ответ из кэша (15 минут — так часто Open-Meteo обновляет текущие данные). Если сервис погоды недоступен, карточка пишет об этом, а остальное показывает.
- Границы участка скачиваются в GeoJSON или архивом Shapefile (backend/pr-032) — для ГИС агронома или соседнего сервиса.
- Удаление — с подтверждением прямо в карточке (без системного окна `confirm`, которое не переводится и выглядит чужим). После удаления карточка закрывается, а участки на карте и сводка по районам обновляются.
- Карточка стала выше, поэтому открывается всегда над точкой клика, а карта плавно сдвигается так, чтобы точка оказалась ниже центра и карточка не обрезалась краем карты.

## Динамика вегетации участка (pr-056)

- В карточке участка — кнопка «Динамика вегетации»: окно с графиком NDVI и NDRE за сезон по снимкам Sentinel-2 (backend/pr-069), сводкой (последний NDVI, сколько снимков без облаков и сколько закрыто облаками над участком), таблицей значений и кнопкой «Обновить по новым снимкам» (фоновая задача backend/pr-060). Пока расчёт идёт, история перезапрашивается раз в 30 секунд — снимки сохраняются по одному, и график растёт на глазах. Окно монтируется только открытым, чтобы история не запрашивалась при каждом открытии карточки.
- График нарисован своим SVG-компонентом, а не библиотекой из плана pr-055 (Recharts тянет Redux Toolkit и десяток пакетов, а здесь нужны две линии). Оба индекса в одних единицах (−1..1), поэтому у графика одна ось; ось Y — от 0 (ниже, если индекс отрицательный) до 1, деления оси времени — начала месяцев.
- Облачные снимки на линию не попадают (пропуск, а не ноль), но видны в таблице с прочерком и облачностью над участком.
- Цвета линий — отдельные токены темы `--chart-ndvi` и `--chart-ndre`, подобранные валидатором палитры: различимость при нарушениях цветового зрения (ΔE не меньше 18 у пары), полоса светлоты и контраст с поверхностью проверены отдельно для светлой и тёмной темы. Серии различаются не только цветом: легенда над графиком и подписи у концов линий.
- Наведение показывает вертикальную линию и подсказку ближайшего снимка (дата, NDVI, NDRE); область наведения — весь график, а не тонкие линии. Те же значения доступны с клавиатуры и экранному диктору в таблице, а у графика текстовое описание (число снимков и период).
- Модальное окно получило размер `lg` для графиков и таблиц.

## Риск болезней на участке (pr-058, часть pr-057)

- В карточке участка — уровни риска милдью и оидиума на сегодня (вне сезона — на последний день с оценкой) и кнопка «Риск по дням». Окно показывает риск сегодня с объяснением (идёт ли инкубация милдью и сколько пройдено, ожидаются ли пятна, индекс оидиума), неделю вперёд по прогнозу погоды и сезон на графиках; кнопка «Пересчитать по свежей погоде» вызывает пересчёт на сервере (backend/pr-077), ответ сразу обновляет данные.
- Уровень — значок с иконкой и словом («низкий», «средний», «высокий»), цвет только дополняет: уровни читаются и без различения цветов. Зелёный, жёлтый и красный зарезервированы за уровнями риска и не используются для линий графиков.
- Милдью по дням — худший уровень из «трёх десяток» и модели Гойданича; оидиум — индекс Gubler-Thomas. «Сегодня» — по времени Кишинёва, как и сутки агромоделей на сервере.
- Индекс Gubler-Thomas (0..100) и продвижение инкубации (0..100 %) измеряют разное, поэтому это два графика друг под другом с общей шкалой времени, а не две линии на одной оси. На графиках — линия «сегодня» и затенённая область прогноза; на графике милдью треугольники на оси отмечают дни заражения по «трём десяткам» (с подписью при наведении).
- График из окна динамики вегетации вынесен в общий компонент `TimeSeriesChart` (одна ось, деления по месяцам, подсказка при наведении, линия «сегодня», метки событий); подписи у концов линий — только когда линий несколько: одну линию называет заголовок.
- Под окном — оговорка: агромодели оценивают условия для болезни по погоде, а не её наличие; решение об обработке принимает агроном.

## Раскраска участков по риску (pr-025)

- Карта берёт уровни на сегодня одним запросом `GET /risks/today` (backend/pr-079), а не риском каждого участка: участков на карте может быть много.
- Цвет участка — худший уровень из милдью и оидиума: красный — высокий, янтарный — средний. Низкий риск и участки без оценки (вне сезона, апрель–сентябрь) остаются изумрудными, как растительность.
- Цвета те же, что у значков уровней (`RiskBadge`), и зарезервированы за риском. Легенда показывается поверх карты слева внизу только когда есть оценки на сегодня; вне сезона она не нужна.

## Справка по болезням (pr-050)

- Под результатом диагностики — карточка «О болезни»: признаки, погода, при которой болезнь развивается, и что делать. Тексты лежат в переводах RU/RO/EN, а не приходят с сервера: их шесть и они меняются редко.
- Названий препаратов и доз нет: они зависят от государственного реестра разрешённых средств и решаются с агрономом, о чём сказано в карточке. Для милдью и оидиума карточка отсылает к риску на карте — он показывает, когда обрабатывать.

## Главная — сводка хозяйства (pr-053)

- Главная открывается в макете кабинета с боковым меню и показывает плитки: число участков, общую площадь, сколько участков сегодня в высоком и среднем риске. Ниже — таблица участков с уровнями милдью и оидиума на сегодня, опасные — первыми.
- Данные — те же запросы, что у карты (`/vineyards` и `/risks/today`), поэтому переход между главной и картой не загружает их заново.
- Вне сезона в плитках риска стоит прочерк, а не ноль: «0 участков в риске» читалось бы как «всё хорошо», хотя оценок просто нет.

## Погода рядом с риском (pr-057)

- В окне «Риск по дням» — температура и осадки сезона на двух графиках, по одной оси на каждом: у них разные единицы, а две оси на одном графике легко прочитать неверно. Дни заражения по правилу «трёх десяток» отмечены на обоих, поэтому видно, какой дождь и какая температура к ним привели.
- Погода берётся из факторов модели Гойданича (backend/pr-057): модель считается каждый день сезона и хранит среднюю температуру и осадки дня. Отдельного эндпоинта погоды за сезон не понадобилось.
- Осадки — столбцами (величина за сутки), температура — линией. В `TimeSeriesChart` у серии появился вид `bar`. В записях, посчитанных до появления осадков, графика осадков нет, пока риск не пересчитан.

## Экспорт карты в PNG (pr-033, первая часть)

- Кнопка «Сохранить карту в PNG» в панели инструментов сохраняет видимую часть карты с участками и слоями, без панелей интерфейса.
- Пиксели WebGL читаются в обработчике `render` того же кадра (`once('render')` + `triggerRepaint`): буфер после кадра очищается, а `preserveDrawingBuffer` замедлил бы карту всё время, а не только при сохранении.
- На картинку дорисовывается подпись источников из углового блока карты: лицензия OpenStreetMap требует указывать её и на сохранённых изображениях. Размер шрифта учитывает плотность пикселей экрана.
- PDF — позже: PNG вставляется в отчёт и письмо и так.

## GPS из EXIF фото (pr-038)

## PWA: манифест и Service Worker (pr-069)

- `vite-plugin-pwa` 2.0.0 (Workbox, режим generateSW): манифест с названием, цветом темы и значками 192, 512 и маскируемым 512 (эмблема в безопасной зоне на белом фоне), Service Worker с предзагрузкой оболочки — код, стили, шрифты, значки. Лимит предзагрузки поднят до 4 МБ: фрагмент с MapLibre больше 2 МБ по умолчанию.

## Индикатор сети (pr-075)

- `useOnlineStatus` — `useSyncExternalStore` поверх `navigator.onLine` и событий `online`/`offline`. Это признак подключения к сети, а не доступности сервера: ошибки сервера по-прежнему показывают сами запросы.
- Пока сети нет, под шапкой кабинета — жёлтая полоса: показаны уже загруженные данные, а анализ фото, пересчёт риска и сохранение участков заработают, когда сеть вернётся. Запросы TanStack Query без сети и так ставятся на паузу и продолжаются сами.

## Кэш карты для работы без сети (pr-070)

- В предзагрузку Service Worker добавлены границы районов (GeoJSON) и шрифт подписей карты (`.pbf`) — около 300 КБ.
- Плитки подложки OpenStreetMap и Esri кэшируются по мере просмотра (CacheFirst, до 1000 плиток на источник, 7 дней, очистка при нехватке места). Заранее ничего не скачивается: правила tile.openstreetmap.org запрещают массовую загрузку.
- `clientsClaim`: при первой установке Service Worker сразу обслуживает открытую страницу, иначе плитки первого визита прошли бы мимо кэша. Новые версии по-прежнему ставятся по кнопке «Обновить».
- Данные участков без сети берутся из кэша запросов открытой вкладки; после перезагрузки без сети нужен вход, а он требует сервера — сохранение данных между запусками придёт с локальной очередью (pr-076).
- Попутно исправлена ошибка: при уходе со страницы карты MapView удалял карту раньше, чем Terra Draw снимал свои слои, и страница падала с «Что-то пошло не так». Остановка рисования теперь, как и снятие слоёв участков, переживает уже удалённую карту.
- Проверено на сборке: 33 плитки в кэше после просмотра, без сети переход на карту показывает подложку, участки и границы.

## Диагностика без сети на устройстве (pr-071 — pr-074)

- Классификатор тот же, что на сервере (EfficientNet-B0, ONNX, 15,3 МБ): сервер отдаёт файл и описание (`/ai/models/classifier`, backend PR #62), браузер хранит его в IndexedDB вместе с версией — началом SHA-256. Если на сервере версия новее, карточка предлагает обновить копию.
- Движок — `onnxruntime-web` 1.30.0 (та же версия, что onnxruntime на сервере), сборка `wasm`: только процессор, файл WebAssembly 14 МБ со своего сервера, а не с CDN, — иначе без сети не загрузится сам движок. Один поток: многопоточность требует изоляции страницы (COOP/COEP).
- Анализ — в Web Worker: фото сжимается в квадрат 224×224 (`createImageBitmap` + `OffscreenCanvas`), нормализуется так же, как на сервере (`leafTensor`), ответ — softmax и классы по убыванию. Результат — в том же виде, что у сервера, с тем же порогом уверенности 0,6, но без тепловой карты и маски поражения: модель U-Net (98 МБ) в браузер не скачивается.
- Без сети кнопка «Определить болезнь» отправляет фото модели на устройстве; без скачанной модели — объясняет, что её нужно скачать. Источник запоминается при нажатии, и над результатом написано, что он получен на устройстве.
- Найдено при проверке: TanStack Query без сети ставит мутации на паузу, и анализ на устройстве «висел». Локальным мутациям (анализ, удаление модели) задан `networkMode: 'always'`. Ошибка загрузки потока отклоняет ждущие запросы, а не оставляет их висеть. В предзагрузку добавлены `.mjs` — загрузчик движка; сам `.wasm` сохраняется Service Worker при скачивании модели.
- Проверено в браузере на сборке: на фото листа с чёрной гнилью сервер — «чёрная гниль, 93 %», устройство без сети — «чёрная гниль, 92 %». Небольшая разница — от способа сжатия фото (браузер и Pillow сжимают по-разному); на одном снимке это проверка работоспособности, а не оценка точности.

## Камера в приложении (pr-078, pr-079)

- Кнопка «Сфотографировать лист» на сенсорном экране открывает камеру прямо в приложении (`getUserMedia`, задняя камера, до 1920×1080) — с рамкой-подсказкой «лист целиком» и подсказкой о свете. Системная съёмка через `capture` давала фото, но без рамки и без управления камерой. Где браузер камеру не даёт, остаётся прежний `capture`.
- Вспышка (`torch`) и зум — через `applyConstraints`, и только если камера их умеет (`getCapabilities`): многие браузеры и камеры их не дают, тогда кнопок просто нет. Не принятая камерой вспышка возвращает кнопку в прежнее состояние, не принятый зум не мешает снимать.
- Снятый кадр становится JPEG-файлом и идёт тем же путём, что фото из галереи (проверка формата, координаты, анализ). Камера выключается сразу после съёмки или закрытия окна — иначе горит индикатор и садится батарея; если поток открылся уже после закрытия окна, он тоже выключается.
- Отказ в доступе, отсутствие камеры и сбой объясняются отдельно, с подсказкой выбрать фото из галереи.
- Проверено в браузере с тестовой камерой Chrome на экране телефона: видео 1920×1080 в рамке, «Снять» — кадр 1920×1080 в загрузчике, камера выключена. Вспышку и зум тестовая камера не умеет: они проверены тестами.

## Карта на сенсорном экране (pr-080)

- Кнопка «Моё местоположение» (`GeolocateControl`): точка и круг точности, при обходе виноградника точка следует за человеком (высокая точность GPS, приближение не дальше 17-го масштаба).
- На сенсорном экране (`pointer: coarse`) допуск касания поднят с 3 до 6 пикселей: палец всегда чуть сдвигается, и касание участка считалось перетаскиванием — карточка не открывалась. Поворот и наклон щипком двумя пальцами отключены: при обычном приближении карта переворачивалась, а с севером вверху участки привычнее; повернуть можно кнопкой компаса. С мышью всё как прежде.
- Проверено в эмуляции телефона с заданными координатами: точка местоположения внутри «Тестового участка 1», касание участка открывает его карточку.

## История проверок (pr-045 — pr-047)

- На странице диагностики галочка «Сохранить фото и результат в историю» (включена по умолчанию) и выбор участка. Участок подставляется по GPS из фото (pr-038), но его можно сменить или выбрать «Без участка». Сохранение — по выбору пользователя: фото уходит в хранилище только с его согласия. Без сети анализ идёт на устройстве и не сохраняется — поле сохранения скрыто.
- Логика «где снято и на каком участке» вынесена в хук `usePhotoLocation`: им пользуются и подпись под фото, и выбор участка.
- Страница «История» (`/history`, пункт меню и нижней панели): карточки с фото, диагнозом, уверенностью, участком и временем, по 12 на страницу, новые первыми. Фильтры — диагноз, участок, даты «с» и «по»; новые условия начинают с первой страницы, а прежняя страница видна, пока грузится следующая.
- Фото приходит с сервера с заголовком авторизации, поэтому не ссылкой в `<img>`, а файлом (blob), из которого делается временная ссылка; браузер держит его в кэше запросов.
- Удаление — в два шага («Удалить» → «Удалить проверку?»): вместе с проверкой удаляется и фото.
- Формы числа «проверка / проверки / проверок» — по правилам i18next для каждого языка; в общей схеме ключей у английского и румынского есть и неиспользуемые формы.
- Проверено в браузере: фото с координатами участка сохранено на этом участке и показано в истории с фото.

## Заключение агронома в истории (pr-044)

- В карточке проверки — заключение агронома, если оно есть: «Мария: диагноз подтверждён» или «Мария: на самом деле — милдью» с комментарием. Ответ модели остаётся заголовком карточки: заключение не подменяет его, а стоит рядом.
- Кнопка «Заключение» — только у агронома и администратора (роль из профиля, `GET /users/me`). Окно: «модель права» или «на фото другое» с выбором правильного диагноза (ответ модели в списке не предлагается), комментарий до 1000 знаков, «Отозвать заключение», если оно уже есть. Окно создаётся только открытым — каждый раз начинается с текущего заключения.
- Проверено в браузере под учётной записью агронома: заключение «на самом деле — милдью» с комментарием сохранилось и показано в карточке.

## Рекомендации по дням (pr-059)

- В окне «Риск по дням» таблица «Что делать: сегодня и неделя вперёд»: дата, уровни милдью и оидиума и что делать в этот день. Рекомендации не новый прогноз, а перевод состояния тех же агромоделей в действие (`dayAdvice`):
  - заражение по «трём десяткам» — системный препарат в первые дни после заражения, если до дождя не было защитной обработки;
  - инкубация по Гойданичу на 60 % и выше — осмотр нижней стороны листьев; ожидаются пятна — осмотр и удаление поражённых листьев;
  - индекс Gubler-Thomas от 60 — сера или системный препарат и проветривание кроны; от 30 — осмотр листьев и гроздей;
  - иначе — «опасных условий нет».
- Названий препаратов и доз нет, как и в справке по болезням: под таблицей та же отсылка к государственному реестру и агроному. Дни после сегодняшнего — по прогнозу погоды, это сказано в заголовке.
- Вне сезона (октябрь — март) моделей нет, и таблица не показывается.

## Картограмма NDVI на карте (pr-030)

- В блоке «Слои» — переключатель «Картограмма NDVI». Включённый слой показывает над каждым участком из фильтра картограмму последнего снимка без облаков (backend/pr-063): пиксели Sentinel-2 по 10 м, от красного (почва) до зелёного (густая листва). Под переключателем — шкала 0..1 той же палитры и подсказка, что делать, если слоя нет.
- Картограмма — слой-картинка MapLibre по четырём углам с сервера: перепроецировать её на клиенте не нужно. Пиксели не сглаживаются (`raster-resampling: nearest`): на карте виден настоящий шаг снимка.
- Слой лежит над заливкой участка и под его контуром и подписью — граница участка видна поверх снимка.
- PNG приходит с заголовком авторизации, поэтому загружается файлом (blob) и подаётся карте временной ссылкой, как фото в истории. История снимков участка берётся из того же кэша запросов, что и окно динамики вегетации; картинка снимка не перезапрашивается.
- Запросы идут только при включённом слое: история каждого участка — отдельный запрос, а участков у хозяйства единицы или десятки.
